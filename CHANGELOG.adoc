== 0.1.5 (29 avril 2026)

=== Modifié

* **Repo GitHub renommé** `aloli-crystal/crystal-api-dedibox` →
  `aloli-crystal/api-dedibox` (convention de nommage Aloli : les
  créations originales abandonnent le préfixe `crystal-`). Les anciens
  liens redirigent automatiquement.
* Champ `name:` du `shard.yml` mis à jour de `dedibox-api` à `api-dedibox`
  (alignement avec le nom du repo). Le module reste `DediboxApi`
  (sémantiquement plus naturel).
* Nouveau fichier d'entrée shim `src/api-dedibox.cr` (charge
  `src/dedibox_api.cr`) ; `require "dedibox-api"` devient
  `require "api-dedibox"`.

== 0.1.4 (24 avril 2026)

=== Ajouté

* Constante `DediboxApi::Endpoints::Servers::DEFAULT_RESCUE_IMAGE`
  (= `"debian-12_amd64"`), remontée depuis beryl où elle était
  hardcodée. Debian 12 reste le choix par défaut le plus stable
  pour héberger un environnement de provisioning (mfsBSD-in-QEMU,
  scripts shell, …) et disponible sur toutes les offres Dedibox
  fin 2026.

=== Modifié

* `servers.prepare_rescue(id, image)` : `image` devient optionnel
  avec pour valeur par défaut `DEFAULT_RESCUE_IMAGE`. L'appelant
  peut maintenant écrire `servers.prepare_rescue(id)` sans
  redéclarer le slug côté client. Rétrocompatible : les appels
  existants qui passent `image` continuent de fonctionner.

== 0.1.3 (24 avril 2026)

=== Ajouté

* `servers.reboot_to_disk(id, reason)` : helper qui enchaîne
  `boot_normal(id)` puis `reboot(id, reason: …)`. Équivalent
  sémantique du `boot_from_disk` OVH — évite au caller de
  connaître la séquence à deux étapes propre à Dedibox (sans
  `boot_normal` préalable, un simple `reboot` laisse le serveur
  en rescue). Retourne `false` si `boot_normal` est refusé, sans
  tenter le reboot.

== 0.1.1 (24 avril 2026)

=== Ajouté

* `servers.update_hostname(id, name)` : modifie le hostname affiché
  dans la console Dedibox via `PUT /server/{id}` avec
  `{"hostname": "..."}`. Validé live sur serveur 186260.
* `user.info` : `GET /user` → login, email, nom, société du compte
  propriétaire du token. Utile pour `beryl init` (confirmer à quel
  compte correspond le token avant d'écrire la config).
* `DediboxApi::Endpoints::UserInfo` struct avec `#display_name` qui
  assemble `first_name` + `last_name` et tolère les champs absents.

=== Limitations documentées

* API Dedibox n'expose PAS d'endpoint public pour modifier le reverse
  DNS. Les tentatives `POST /server/{id}/reverse`, `PUT /reverse/{ip}`,
  `POST /reverse` retournent toutes « Unknown method ». L'opération
  passe par la console web ou un ticket support.
* Pas d'info disques/RAID côté API — à récupérer en SSH depuis le
  rescue (c'est ce que fait `beryl scan`).

== 0.1.0 (24 avril 2026)

=== Ajouté

==== Fondations du projet

* Squelette initial (`shard.yml`, `LICENSE` MIT, README).
* Convention Aloli : branche par défaut `production`, messages de
  commit en français, licence MIT, auteurs `ALOLI sas`.

==== Cœur du client

* `DediboxApi::Client` : authentification par `Authorization: Bearer`,
  sans signature ni offset d'horloge (API Dedibox simple comme
  Scaleway, contrairement à OVH).
* Endpoint par défaut `https://api.online.net/api/v1`, surchargeable
  pour les tests ou un proxy.
* Transport HTTP abstrait `DediboxApi::HttpTransport` avec
  implémentation `DefaultHttpTransport` (stdlib `HTTP::Client`) ;
  permet l'injection d'un double en test via `StubTransport`.

==== Endpoints de provisioning (serveurs)

* `servers.list` : `GET /server/` → liste normalisée d'IDs entiers
  (Dedibox renvoie des URIs `/api/v1/server/X`, on extrait l'entier).
* `servers.info(id)` : `GET /server/{id}` → struct {Server} avec
  accès typé (`id`, `offer`, `hostname`, `power`, `boot_mode`,
  `public_ip`, `public_reverse`, `ips[]`).
* `servers.rescue_images(id)` : `GET /server/rescue_images/{id}` →
  slugs d'images disponibles (ex. `debian-12_amd64`,
  `ubuntu-22.04_amd64v2`).
* `servers.prepare_rescue(id, image)` : `POST /server/boot/rescue/{id}`
  → positionne `boot_mode` à `rescue`, retourne {RescueCredentials}
  (login `sd-<id>`, password généré, IP, protocole).
* `servers.reboot(id, reason)` : `POST /server/reboot/{id}?reason=…`
  → reboot effectif. `reason` est OBLIGATOIRE côté API Dedibox (sans,
  retourne `false` silencieusement).
* `servers.boot_normal(id)` : `POST /server/boot/normal/{id}` →
  retour boot disque (post-bootstrap).

==== Clés SSH IAM

* `ssh_keys.list`, `ssh_keys.info(id)`, `ssh_keys.create(desc, key)`,
  `ssh_keys.delete(id)` — gestion du trousseau global du compte.
  Les clés IAM sont injectées automatiquement par Dedibox dans tout
  passage en rescue (pas besoin de lier une clé à un serveur).

==== Taxonomie d'erreurs

* `DediboxApi::ApiError` (base).
* `AuthenticationError` (HTTP 401/403 — token invalide ou révoqué).
* `NotFound` (HTTP 404).
* `RateLimited` (HTTP 429, expose `retry_after`).
* `ApiError` (autres, expose `status_code` et `error_code` — qui
  correspond au champ `code` dans le format Dedibox
  `{"error":"...","code":N}`).

==== Découvertes API (format exact confirmé en live)

* `POST /server/rescue/{id}` retourne « Unknown method » — la forme
  correcte est `POST /server/boot/rescue/{id}`.
* `POST /server/reboot/{id}` sans `reason=` → `false` silencieux ;
  avec `?reason=...` → `true` et reboot effectif.
* `POST /server/boot/normal/{id}` (pas `/server/boot_normal/{id}`).
* Le reverse DNS est lu via `Server#ips[].reverse` — il n'y a pas
  d'endpoint dédié.
